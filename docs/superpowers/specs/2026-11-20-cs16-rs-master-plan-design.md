# cs16-rs — мастер-план до 95–99%

Дата: 2026-11-20. Статус: черновик, ждёт одобрения.

## 0. Коротко

- Сейчас: 26.6k строк, 8 crates, офлайн-игра с ботами. Оценка ~25% (экспертная, не замер).
- Цель: CS 1.6 на Rust, которая играет вместе с оригиналом в обе стороны, запускается в браузере, расширяется модами без Metamod/AMX и поднимает сервер одной командой.
- Способ: один язык сообщений (Protocol 48) поверх сменного транспорта, симуляция на модели энтити GoldSrc, клиентское ядро без привязки к платформе.
- Мера: реестр паритета. Процент считается инструментом, а не на глаз. В зачёт идёт только то, что сверено с оригиналом.
- Объём: ещё примерно 180–250k строк (оценка). 14 фаз, после фазы 3 большинство идут параллельно.

## 1. Зачем

Слова владельца проекта: «просто на расте пизже», веб-версия, моды «как в майне, без сторонней херни», запуск серверов, оригинал и порт «взаимосвязаны».

Из этого следует:

1. Порт должен быть лучше оригинала в эксплуатации, а не музейной копией. Аутентичность — режим по умолчанию, улучшения — опции.
2. Браузер — платформа первого класса, а не побочная сборка.
3. Моды — встроенная функция движка: кинул файл в папку, работает; зашёл на сервер — мод скачался сам.
4. Совместимость по сети двусторонняя: оригинальный клиент ↔ наш сервер, наш клиент ↔ оригинальный сервер.

## 2. Цели, не-цели, анти-цели

### Цели

| № | Цель | Как проверяется |
|---|---|---|
| G1 | Оригинальный клиент CS 1.6 (текущая Steam-сборка, Protocol 48) играет полный матч на `cs-server` | Ручной прогон + headless-зонд + разбор pcap |
| G2 | Наш клиент играет на стоковом HLDS и на ReHLDS + ReGameDLL + AMX Mod X | Чек-лист сценариев на эталонном стенде |
| G3 | Клиент работает в браузере (WebGPU, запасной WebGL2), заходит на наш сервер напрямую, на оригинальный — через релей | Сборка `wasm32-unknown-unknown` в CI + ручной прогон |
| G4 | Моды на WASM: серверные, клиентские, ассет-паки; автозагрузка с сервера; песочница | Набор эталонных модов в репозитории |
| G5 | Сервер одной командой, один бинарь, без внешних зависимостей; раздаёт веб-клиент сам | `cs-server --map de_dust2` → открыть `http://ip:27016` |
| G6 | Поведение геймплея совпадает с ReGameDLL в пределах допусков | Дифференциальные тесты против эталона |
| G7 | Процент готовности считается автоматически | `cargo xtask parity` |

### Не-цели (сознательно вне 100%)

- Steam-авторизация и VAC. Нужна нативная библиотека Valve. Следствие: наш клиент не заходит на серверы с проверкой Steam; работает с LAN и non-Steam серверами.
- Нативные плагины Metamod (x86 DLL). Замена — WASM-моды и слой совместимости с `.amxx` (фаза 11).
- Побитовое совпадение float-вычислений с оригиналом. Допуски заданы в п. 7.
- Одиночная игра, сохранения, Condition Zero career/tutor.
- Хранение ассетов Valve в репозитории или на наших серверах.

### Анти-цели (провал, даже если технически работает)

- Два разных кода мира в клиенте (свой и «для чужих серверов»).
- Улучшения, которые ломают совместимость по умолчанию.
- Процент готовности, выставленный вручную.
- `unsafe` в собственном коде workspace.
- Открытый UDP-релей без ограничений (см. п. 8, безопасность).

## 3. Подходы

| | Суть | Цена | Вердикт |
|---|---|---|---|
| **A** | Все общаются сообщениями Protocol 48; меняется только транспорт (UDP+netchan, WebSocket, WebTransport, loopback). Моды — через usermsg | Перевод симуляции на энтити GoldSrc; `cs-net` выкидывается | **Выбран** |
| B | Свой протокол `postcard` + шлюз в Protocol 48 | Мало переделок сейчас | Отклонён: две модели мира в клиенте, каждая фича дважды |
| C | Только Protocol 48 по UDP | Минимум кода | Отклонён: браузер всегда через прокси, даже к своему серверу |

Выбор A — моё решение: владелец проекта отдал выбор («не знаю»). Причина: это единственный вариант, где G1–G4 не конфликтуют. Локальная игра тоже идёт через тот же путь (loopback-транспорт), поэтому одиночный режим и сеть не расходятся никогда.

### 4.2 Потоки данных

```
оригинальный клиент ──UDP/netchan──┐
наш нативный клиент ──UDP/netchan──┤
наш веб-клиент ──WebSocket/WT──────┼─► cs-transport ─► cs-engine ◄─► cs-sim ◄─► cs-mod-host
локальная игра ──loopback──────────┘                     │
                                                         └─► cs-bot

cs-clientcore ◄─ cs-transport ◄─ (наш сервер | HLDS | ReHLDS | cs-relay)
      │
      ├─► cs-client (winit + wgpu + звук + UI)
      ├─► cs-web    (то же под wasm)
      └─► cs-probe  (без окна)
```

### 4.3 Граница движок ↔ игра

`cs-engine` и `cs-sim` связаны двумя трейтами, по духу повторяющими `enginefuncs_t` и `DLL_FUNCTIONS`:

- `EngineApi` (движок даёт игре): создать/удалить edict, precache, `set_model`, `set_origin`, трассировки, `emit_sound`, `message_begin/write_*/message_end`, cvar, команды сервера, `find_entity_*`, PVS-запросы.
- `GameDll` (игра даёт движку): `game_init`, `spawn`, `think`, `touch`, `use`, `client_connect`, `client_put_in_server`, `client_command`, `client_userinfo_changed`, `player_pre_think/post_think`, `cmd_start/cmd_end`, `add_to_full_pack`, `update_client_data`, `get_weapon_data`, `start_frame`, `server_activate/deactivate`.

Эта же граница — поверхность хуков для модов: каждый вызов `GameDll` и каждый вызов `EngineApi` оборачивается цепочкой pre/post, как hookchains в ReAPI.

## 5. Реестр паритета — как считается процент

`docs/parity/*.toml`, по файлу на категорию. Каждая строка — один проверяемый элемент оригинала.

Статусы: `missing` → `implemented` → `tested` (есть юнит-тест) → `verified` (сверено с оригиналом: golden-захват, дифференциальный тест или пункт ручного чек-листа с датой).

`cargo xtask parity` печатает таблицу и итог. В заголовочный процент идёт только `verified`.

| Категория | Вес | Откуда берётся список |
|---|---|---|
| Сообщения `svc_*` (0–59) и `clc_*` (0–11), чтение и запись | 8 | Константы уже в `cs-proto48/src/messages.rs` |
| Usermsg CS (сейчас зарегистрировано 73) | 6 | Перехват `svc_newusermsg` с эталонного сервера |
| Поля delta (`delta.lst`) | 3 | Файл из установленной игры |
| Temp entities `TE_*` | 4 | Константы SDK |
| Классы энтити карт и игры | 12 | Список классов эталонного `mp.dll` + энтити всех стоковых карт |
| Оружие, предметы, экономика | 10 | Таблицы ReGameDLL |
| Движение (`pm_shared`) | 8 | Набор трасс usercmd |
| Cvar и команды, клиент и сервер | 6 | Дамп `cvarlist`/`cmdlist` с оригинала |
| Рендер: режимы, эффекты, модели | 10 | Чек-лист + эталонные скриншоты |
| Звук | 4 | Чек-лист |
| HUD, меню, VGUI-панели | 8 | Файлы `resource/` + чек-лист |
| Движок: ресурсы, демо, rcon, логи, запросы | 7 | Чек-лист |
| Боты | 4 | Чек-лист поведения |
| Веб | 5 | Чек-лист |
| Моды | 5 | Эталонные моды |

Веса — моё предложение, правятся одним файлом. Списки не выдумываются: каждый снимается с эталона в фазе 0.

## 6. Фазы

Формат: что делаем → что на выходе → условие выхода. Оценки строк — прикидка.

### Фаза 0 — фундамент и мера (~3k строк)

1. Закоммитить `cs-proto48`.
2. Решить вопрос лицензии (п. 8, риск R1) до того, как кода станет в десять раз больше.
3. `xtask parity` + первые реестры: svc/clc, usermsg, delta, cvar/cmd.
4. Эталонный стенд на машине разработчика: HLDS (SteamCMD, app 90), оригинальный клиент, опционально ReHLDS + ReGameDLL + AMX Mod X.
5. `xtask golden`: запись UDP-обмена эталонной пары клиент–сервер в файлы; тест «парсер разбирает захват полностью, без `Ignored` и без остатка байт».
6. `cs-platform`: часы, файлы конфигов, энтропия за трейтами. Убрать прямые `std::fs`, `Instant::now`, `std::thread::sleep` из библиотечных crates (сейчас они в `cs-client/src/app.rs`, `cs-cvar/src/lib.rs`, `cs-vfs`, `cs-net`).
7. CI: `clippy -D warnings`, тесты, `cargo check --target wasm32-unknown-unknown` для всех библиотечных crates.

Выход: `cargo xtask parity` выдаёт число; захват реального входа на сервер разбирается парсером; известно, что в `cs-proto48` не покрыто (в частности BZ2-сжатие фрагментов netchan и полный разбор `svc_temp_entity`, сейчас это `raw`).

### Фаза 1 — энтити-ядро и сервер Protocol 48 (~15k)

Якорь всей сверки: оригинальный клиент заходит на наш сервер.

1. `cs-engine::edict`: пул edict, `EntVars` (origin, angles, velocity, modelindex, sequence, frame, body, skin, effects, rendermode, renderamt, solid, movetype, flags, …), приватные данные игры, серийные номера.
2. Таблицы precache: модели, звуки, generic, события, декали; лимиты как в оригинале.
3. Connectionless: `getchallenge`, `connect`, отказ с причиной, A2S_INFO/PLAYER/RULES, пинг.
4. Сессии: netchan на клиента, munge, надёжный поток, фрагменты, таймауты, rate.
5. Signon: `svc_serverinfo`, `svc_deltadescription`, `svc_newmovevars`, `svc_newusermsg`, `svc_resourcelist`, consistency, `svc_spawnbaseline`, `svc_signonnum`, команды `new`/`sendres`/`spawn`/`sendents`.
6. `clc_move` → usercmd с `msec` → `pmove`. Защита от спидхака по сумме `msec`.
7. Построение кадра: `svc_clientdata` + `svc_packetentities`, delta от подтверждённого клиентом кадра, отсечение по PVS, `add_to_full_pack`.
8. `svc_time`, `svc_pings`, `svc_updateuserinfo`, `svc_setangle`, `svc_lightstyle`, `svc_sound`, `svc_stufftext`, `svc_print`, `svc_disconnect`.
9. Смена карты и переподключение.
10. `cs-transport`: трейт + UDP + loopback.

Выход: оригинальный клиент командой `connect` заходит на `cs-server`, видит карту и других игроков, бегает без рывков и рассинхрона 10 минут. `cs-probe` повторяет это без окна в тесте.

Допущение для проверки на этом шаге: Steam-клиент заходит на сервер, который принимает тикет без проверки (как `sv_lan 1`).

### Фаза 2 — игра на энтити (~20k)

1. Перенос `MatchWorld` на edict: игроки, оружие как отдельные энтити, гранаты, C4, заложники, двери, breakable, выброшенное оружие (`weaponbox`), трупы.
2. Оружие с данными для клиентского предсказания: `weapon_data`, поля `clientdata`, события из `events/*.sc`, общий генератор случайных чисел по seed из usercmd — разброс совпадает с тем, что предсказал клиент.
3. Все usermsg, которые шлёт ReGameDLL при обычном матче: `CurWeapon`, `WeaponList`, `AmmoX`, `Health`, `Battery`, `Money`, `RoundTime`, `ScoreInfo`, `TeamInfo`, `TeamScore`, `DeathMsg`, `SayText`, `TextMsg`, `StatusIcon`, `BarTime`, `Radar`, `BombDrop`, `ScreenFade`, `ScreenShake`, `SetFOV`, `HideWeapon`, `VGUIMenu`, `ShowMenu`, `MOTD`, `ServerName`, `SendAudio`, `NVGToggle`, `Crosshair`, `ResetHUD`, `InitHUD` и остальные по реестру.
4. Клиентские команды: `jointeam`, `joinclass`, `chooseteam`, `buy`, `buyequip`, `menuselect`, алиасы покупки, `drop`, `say`, `say_team`, `radio1..3`, `nightvision`, `kill`, `vote`, `votemap`, `specmode`.
5. Компенсация лага по семантике `sv_unlag` (сейчас кольцевой буфер 250 мс в `cs-net` — переносится в `cs-engine`).
6. Хитбоксы по реальным костям модели на сервере. Сейчас «анатомические 6 хитбоксов» — приближение; оригинал считает кости студийной модели.

Выход: оригинальный клиент играет полный раунд `de_dust2` и `cs_office` с ботами на нашем сервере; HUD, меню покупки, табло, радар, звуки и анимации оружия корректны. Golden-сравнение потока usermsg с эталонным сервером на одинаковом сценарии.

### Фаза 3 — наш клиент как клиент Protocol 48 (~18k)

1. `cs-clientcore`: машина состояний подключения, signon, загрузка ресурсов, таблицы precache.
2. Хранилище энтити по индексам, baseline, применение delta, интерполяция (`ex_interp`), экстраполяция.
3. Предсказание движения и оружия на общем `pmove` и общих таблицах оружия; сверка по `svc_clientdata`.
4. Диспетчер usermsg → состояние HUD. Регистрация неизвестных сообщений (для модов и AMX).
5. Рендер любой энтити, которую прислал сервер, по `modelindex`: brush-модель, студийная модель, спрайт. Никаких «особых случаев» под свой сервер.
6. Локальная игра = `cs-engine` в том же процессе через loopback.
7. Удалить `cs-net`.

Выход: наш клиент играет на стоковом HLDS (LAN) и на ReHLDS + ReGameDLL + AMX Mod X: текстовые меню, HUD-сообщения, MOTD, смена карты. Локальная игра работает тем же кодом.

**После фазы 3 треки независимы и идут параллельно, каждый в своей сессии и ветке.**

### Фаза 4 — веб (~8k + JS-склейка)

1. `cs-web`: сборка под `wasm32-unknown-unknown`, `wgpu` на WebGPU, запасной WebGL2 (атлас лайтмапов 2048² в лимиты укладывается).
2. Ассеты: пользователь указывает свою папку `Half-Life` (`showDirectoryPicker`, запасной вариант `<input webkitdirectory>`, перетаскивание). `VfsBackend` поверх неё, ленивое чтение, кэш в хранилище браузера.
3. Транспорт: WebSocket (везде), затем WebTransport с датаграммами (меньше задержка).
4. `cs-server --web-port`: принимает WS/WT и сам раздаёт веб-клиент. Сценарий: поднял сервер, отправил другу ссылку, друг указал свою папку игры и зашёл.
5. `cs-relay`: WS→UDP для оригинальных серверов. Встроен в `cs-server` флагом; ограничения — в п. 8.
6. Ввод: захват указателя, raw-мышь где доступна, полноэкранный режим, геймпад, сенсорное управление.
7. PWA: установка, офлайн-запуск с ботами.
8. Stretch: listen-сервер во вкладке браузера (`cs-engine` + `cs-sim` в wasm), игроки подключаются по WebRTC через сигналинг `cs-master`.

Выход: клиент в Chromium и Firefox играет на нашем сервере со стабильным кадром; через релей заходит на оригинальный сервер.

### Фаза 5 — моды v1 (~15k)

1. `cs-mod-api`: версионируемый ABI. Хуки на каждый вызов `GameDll` и `EngineApi` (pre/post, возможность отменить или подменить результат). Нативы: энтити, сообщения, cvar, команды, меню, задачи по таймеру, трассировки, звук, хранилище данных мода.
2. `cs-mod-host`: исполнение WASM. Моё решение для v1 — интерпретатор `wasmi` везде (один код для нативной и веб-сборки, детерминизм, учёт «топлива»). Трейт `ModRuntime` оставляет место для JIT-бэкенда, если упрёмся в скорость.
3. Песочница: нет файлов и сети по умолчанию; права объявляются в манифесте; лимит памяти и топлива на кадр; мод, превысивший лимит, выгружается, сервер живёт.
4. Формат: папка или архив `.csmod` в `mods/`. Манифест `mod.toml`: id, версия, версия API, сторона (server/client/both), зависимости, права, список ассетов.
5. Ассет-паки: слой VFS `mods/<id>/` поверх `cstrike`.
6. Клиентские моды: рисование HUD, свои панели, обработка своих usermsg, ввод.
7. Автозагрузка: сервер объявляет нужные клиентские моды и ассеты; наш клиент скачивает, проверяет хэш, запускает в песочнице. Согласование возможностей — ключ в userinfo; оригинальным клиентам расширенные сообщения не шлются.
8. `cs-mod-sdk`: crate для Rust-модов, макросы хуков, шаблон проекта, горячая перезагрузка на сервере.
9. Эталонные моды в репозитории: deathmatch с возрождением, gungame, зомби-режим, админ-меню, статистика, свой HUD-элемент.

Выход: каждый эталонный мод ставится копированием файла; серверная часть работает и для оригинальных клиентов; клиентская подгружается нашим клиентом автоматически.

### Фаза 6 — паритет движения и оружия (~6k + тесты)

2. Недостающее в `pmove`: вода (уровни, плавание, waterjump), конвейеры, толкаемые объекты, `edgefriction`, движение на движущихся платформах, застревание и выталкивание, все флаги и таймеры.
3. Оружие: сверка каждой пушки — скорострельность, разброс по состояниям, отдача, урон по дистанции, пробитие по материалам, время перезарядки, скорость бега, режимы.
4. Щит, все гранаты по физике оригинала, ослепление по углу и дистанции.

Выход: набор трасс движения проходит в допуске (п. 7); таблица оружия сверена полностью.

## 7. Проверка

| Метод | Что ловит | Где живёт |
|---|---|---|
| Golden-захваты | Ошибки разбора и сборки пакетов | `xtask golden`, файлы захватов вне репозитория, тесты пропускаются при отсутствии |
| `cs-probe` против эталонного сервера | Ошибки клиентской стороны протокола | Интеграционные тесты, требуют стенд |
| Оригинальный клиент против `cs-server` | Ошибки серверной стороны | Ручной чек-лист с датой в реестре |
| Дифференциальные тесты движения | Расхождения `pmove` | Трассы usercmd + эталонные траектории |
| Таблицы оружия | Расхождения урона, разброса, таймингов | Юнит-тесты по таблицам ReGameDLL |
| Эталонные скриншоты | Расхождения рендера и UI | Сравнение с допуском, эталоны у разработчика |
| Property-тесты и фаззинг парсеров | Паники и зависания на мусорном вводе | В workspace — property-тесты; фаззинг — отдельный каталог вне workspace |

Допуски: позиция — 0.03125 юнита (сетка координат протокола), скорость — 0.1 юнит/с, углы — шаг квантования поля delta. Расхождение не должно накапливаться: проверяется на трассах длиной не меньше 60 секунд.

Правило: элемент реестра получает `verified` только с ссылкой на тест или запись в чек-листе.

|---|---|---|
| R1 | **Лицензия.** `Cargo.toml` — MIT, README — «clean-room», а `cs-proto48/src/lib.rs` пишет «ported deterministically from ReHLDS and ReGameDLL_CS». Насколько помню, оба проекта под GPL-3.0; код, производный от них, под MIT выпускать нельзя | Проверить лицензии первоисточников. Затем либо сменить лицензию проекта на GPL-3.0, либо писать по описаниям протокола и собственным захватам, без переноса кода. Решить в фазе 0 |
| R2 | Steam-клиент может отказаться работать с сервером без Steam-аутентификации | Проверяется первым же шагом фазы 1. Запасной путь — режим LAN |
| R3 | Перевод симуляции на edict сломает работающую офлайн-игру | Текущие 4 теста `cs-sim` сохраняются как регрессионные; перенос по одной подсистеме |
| R4 | Открытый релей WS→UDP — готовый инструмент для атак отражением | По умолчанию выключен; список разрешённых адресов, лимит скорости и числа сессий на клиента, только пакеты игрового протокола |

| R7 | Браузер: нет UDP, нет потоков по умолчанию, ограничения на звук до жеста пользователя | Учтено в `cs-platform` и `cs-transport`; звук стартует по клику |
| R8 | В `cs-proto48` нет распаковки BZ2 для фрагментов netchan (поиск по crate ничего не находит), а `svc_temp_entity` сохраняется как `raw` без разбора. Без первого вход на реальный сервер может оборваться на загрузке | Первым делом в фазе 0 по golden-захватам |
| R9 | Объём: 180–250k строк | Параллельные треки после фазы 3; реестр показывает реальный прогресс |
| R10 | Интерпретатор WASM медленный для тяжёлых модов | Трейт `ModRuntime`, JIT-бэкенд позже |

## 9. Мои решения — проверь при чтении

1. Подход A (один язык сообщений, сменный транспорт).
2. Процент считается только по `verified`.
3. Моды — WASM, интерпретатор `wasmi` в v1.
4. Интерфейс строится интерпретатором `.res`, а не кодом на egui.
5. Локальная игра идёт через loopback тем же сетевым путём.
6. Порядок: сначала сеть в обе стороны (фазы 1–3), потом веб и моды. Причина: без этого нечем проверять остальное, а веб-клиент и API модов стоят на тех же границах.
7. Целевая версия оригинала — текущая Steam-сборка CS 1.6. Старые non-Steam сборки — stretch.
8. Веса категорий в реестре.
9. Названия новых crates.

## 10. Что остаётся исполнителю
