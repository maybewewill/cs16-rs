# Checklist: weapons, items and the economy with the original client (phase 2D)

Two parts. Part A is what was already compared with the original game on 2026-11-22 (the registry items marked `verified` point at these lines). Part B is the list of manual checks that are still the project owner's: the original client with `cl_lw 1` (the default) on our server, shooting, buying, reloading and throwing. The automated tests run against `cs-probe` only and compare with the ReGameDLL_CS and ReHLDS source (master, read 2026-11-22); they do not show what the client draws. In the Expected column a value that the source states names the file it comes from; every other value is marked "From memory - confirm": it is what the original game is remembered to show, not something checked, so a difference is a result to write down, not necessarily a bug. No line of Part B is a pass until the owner has filled it in.

## Part A: verified on 2026-11-22 (done by the controller, not the owner)

Original Counter-Strike 1.6 client (Steam, build 10210) and the original HLDS (build 10210), both on this machine. The ledger of the phase (`.superpowers/sdd/2026-11-22-phase2d-weapons/progress.md` and `golden-join-diff.md`) has the full record and the remaining differences.

Method 1: the original client on `cs-server --proto48`, map `de_dust2`, compared with what an original listen server shows. Method 2: golden capture diff, `cs-probe --diff` of a capture of the original HLDS against a capture of our server, for a probe that joins and runs `jointeam 2` and then `joinclass 5` (the probe only talks; it does not shoot).

## Part B: the owner's checks

👤 Run these. Start the server from the repository root:

```
cargo run -p cs-server -- --proto48 --map de_dust2 --port 27015
```

(Set `CS16_GAMEDIR` to the game folder if the server does not find the game: `set CS16_GAMEDIR=D:\SteamLibrary\steamapps\common\Half-Life` in `cmd`.) In the original client open the developer console (`~`) and type `cl_lw 1` (the default; it makes the client predict the weapons and is what the weapon data is for), then `connect 127.0.0.1:27015`. For a second check type `cl_lw 0` and `retry`: the weapon should still work, with the server's events and animations only.

Useful server console commands: `mp_startmoney 16000`, `sv_restart 1`, `mp_freezetime 0`, `mp_roundtime 9`, `mp_friendlyfire 1`, `sv_gravity`. For rows that need a target: a second client or `cargo run -p cs-probe -- --connect 127.0.0.1:27015 --seconds 600 --cmd "jointeam 1" --cmd "joinclass 1"` (a terrorist that stands still). Walk to the buy zone (the spawn area; the green dollar sign shows) and press `b`, or use the aliases of the buy commands.

Fill in the date and the result (pass / fail plus what was seen) of every line. When a line fails, write down what the client showed and what the server window printed.

What is not checked here because it does not exist yet (registry: `docs/parity/weapons.toml`, items `weapon_shield`, `weapon_c4_bomb`, `weapon_vip`, `weapon_bots`, `weapon_autobuy_rebuy`, `weapon_game_player_equip`): the tactical shield, the C4 and the bomb (2E), the VIP, bots, autobuy and rebuy, the `game_player_equip` entity. In progress and fixed in parallel (the controller updates the registry at merge): the flashlight and its battery, the hint messages, the Geiger counter, the pacing of the death think. Known engine gaps that may show as small differences while playing: 36 sounds, 10 models and 5 events that the original's resource list has and ours does not (so a sound or an effect can be silent), the update rate and the frame batching (ours sends about 60 updates a second, the original about 23), `MsgDest::Broadcast` messages going out at the end of the frame instead of with `sv.datagram`, the `sendinfo_time` spacing of userinfo, the delta encoder callbacks (`Player_Encode`, `Entity_Encode`) and the `AddToFullPack` filters.
