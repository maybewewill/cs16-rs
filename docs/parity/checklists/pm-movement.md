# Checklist: player movement with the original client (pm_shared port)

Manual checks of the player movement of `cs-server --proto48` with the original client (Steam CS 1.6, protocol 48). The movement is the original `pm_shared` code ported from ReGameDLL_CS (vanilla branch) behind the engine services ported from ReHLDS (`cs_sim::pm`, `cs-engine`'s `pm` and `texture` modules, `cs-game`'s `pmove.rs`); the registry is `docs/parity/movement.toml`. The automated tests compare with the sources and use `cs-probe` only; this checklist is the comparison with the real client, which predicts its own movement with the same code. 👤 These checks are run by the project owner. In the Expected column a value that the source states names the file or function it comes from (master, read 2026-11-22); every other value is marked "From memory - confirm": it is what the original game is remembered to show, not something checked, so a difference is a result to write down, not necessarily a bug. No line below is a pass until the owner has filled it in.

Because both sides run the same code, any difference between the server's movement and the client's prediction shows up as jitter: the player is pulled back a little now and then, or the view shakes when running along a wall or over steps. Where a row says "jitter" it means that. The client has a console variable that prints or shows its prediction error; From memory - confirm: it is `cl_showerror` (set it to 1, or to 2 for more detail) in the original client, and `net_graph 3` shows the client's own error figures. If neither works, judge by eye.

What is not checked here because it does not exist yet: weapon speeds (`maxspeed` is 240 for everybody, the no-item speed `NO_ITEM_MAX_SPEED` of vanilla `ResetMaxSpeed`, until the weapons of phase 2D; vanilla gives the knife 250 and heavier weapons less, see row 1), bots, the VIP, hostages and the bomb, shields (the `iuser3` shield bit), and the client's own prediction (the Rust client, `cs-client`, still uses the older movement).

Start the server from the repository root:

```
cargo run -p cs-server -- --proto48 --map de_dust2 --port 27015
```

(Set `CS16_GAMEDIR` to the game folder if the server does not find the game: `set CS16_GAMEDIR=D:\SteamLibrary\steamapps\common\Half-Life` in `cmd`.) The server console takes `status`, `sv_restartround 1`, `sv_gravity <n>`, `changelevel <map>` and `quit`.

In the original client, open the developer console (`~`) and type:

```
connect 127.0.0.1:27015
```

Pick a team and an appearance, and wait for the freeze period to end (`mp_freezetime 3` and `sv_restartround 1` in the server console shorten the wait). Rows 12 and 14 need a second player: a second copy of the original client with its own name, or the stand-in `cargo run -p cs-probe -- --connect 127.0.0.1:27015 --seconds 600 --cmd "jointeam 2" --cmd "joinclass 1"` (a probe that joins the counter-terrorists, stands still and so makes no steps of its own; for row 12 the second player has to be a real client that walks). Row 9 needs the ladder map and rows 10 and 11 the water map named there. Fill in the date and the result (pass / fail plus what was seen) of every line. When a line fails, write down what the client showed and what the server window printed.

The maps: the ladder map is `as_oilrig`, the first stock map whose entity lump has a `func_ladder` (found by the automated test `a_ladder_is_climbed_on_a_real_map`; `de_dust2` has no ladder). The water map: `as_oilrig` has `func_water` entities (`func_water_gives_the_player_water_on_a_stock_map`), so try it first. From memory - confirm: `de_aztec` has water too and is a CS map, so try it second. The automated test `water_is_swum_on_a_real_map` uses `c0a0d` from the Half-Life install (the first map in which it found a `!` water pool deep enough), the last fallback. Type `changelevel <map>` in the server console to switch.
